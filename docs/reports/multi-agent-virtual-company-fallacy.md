# 别再给 Agent 发工牌了

> 多 Agent 的价值不在模拟公司，在于更聪明地分配上下文、搜索、验证和执行。

---

## 一个流行的错觉

最近半年，几乎每个 Agent 框架的 demo 都长这样：

一个叫"产品经理"的 Agent 输出需求文档，交给"架构师"Agent 出方案，再交给"开发"Agent 写代码，最后"测试"Agent 跑一遍验收。整个流程像一条微缩版的软件公司流水线，架构图画出来特别好看，给老板汇报的时候一目了然。

我自己也被这个叙事吸引过。直到真正上手做了几轮，才发现一个尴尬的事实：

**这套东西好讲故事，但不好用。**

---

## 我反对的不是多 Agent，是"职能流水线"

先说清楚边界。我不觉得多 Agent 本身有问题。我反对的是一种特定的设计模式——把人类企业的部门分工照搬到模型系统里，让 Agent 像员工一样排队交接。

这里面有三种常见的多 Agent 形态，我的态度完全不同：

| 形态 | 做法 | 我怎么看 |
| --- | --- | --- |
| 职能流水线 | PM → 架构 → 开发 → 测试 | ❌ 大多数情况是伪需求 |
| 并行探索 | 多个 worker 同时搜不同方向 | ✅ 真正有用 |
| 对抗验证 | 一个产出，一个专门挑毛病 | ✅ 真正有用 |

问题不在"多"，在于你为什么要"多"。如果是为了覆盖更大的搜索空间、或者建立独立的质量校验——那是对的。如果只是因为"公司有这些岗位所以 Agent 也该有"——那就是把组织隐喻当成了系统架构。

---

## 为什么流水线式分工跑不通

### 信息每传一次就丢一次

人类团队靠文档交接能运转，不是因为文档写得多完美，而是因为人会自动补足大量没写下来的东西：公司惯例、领域常识、"老王说这个意思其实是那个意思"。

Agent 之间没有这层隐性共识。A 写了一份交接文档给 B，B 拿到的是压缩过的上下文。B 再压缩一次传给 C。每经过一个环节，信息就衰减一轮。

到最后一个 Agent 手里，它看到的已经不是原始问题，而是被反复摘要过的残片。

### 标签不等于能力，但会制造边界

给一个 Agent 写上"你是测试工程师"，它不会因此变得更擅长测试。但它**会**因此更倾向于只做"测试工程师该做的事"。

可现实中很多最有价值的洞察恰恰发生在边界上——测试的人发现了架构缺陷，开发的人意识到需求定义有漏洞。你把职责框死，这些跨界发现就被系统性地压制了。

### 瓶颈根本不在"缺岗位"

我踩过的大部分坑，事后复盘，真正的卡点都不是"Agent 数量不够"或"角色分工不细"，而是：

- 关键上下文漏了，模型在信息不全的情况下硬推
- 搜索空间太窄，只探索了一个方向就锁死了
- 推理到一半链条断了，没有机制恢复
- 长任务跑着跑着状态丢了

这些问题，加再多"岗位"也解决不了。

## 看看头部团队怎么做的

我注意到一个有趣的趋势：真正在生产环境跑多 Agent 的团队，做法和社区里流行的"虚拟公司"路线几乎完全相反。

**Anthropic 的 multi-agent research system**，结构很朴素——一个调度器拆任务，多个 worker 并行去搜索不同方向的信息，最后结果回流统一综合。没有"PM Agent"和"Dev Agent"的区分，所有 worker 都是同质的执行单元。它管用，不是因为模拟了团队协作，而是因为**花了更多 token 覆盖了更多搜索方向**。

**Google 的 context-driven development**，核心理念是把所有关键状态——spec、plan、约束、进度——全部外化到文件里，变成持久资产。这和"Agent 之间口头传文档"是完全相反的方向：前者在减少信息丢失，后者在制造信息丢失。

**OpenAI 对长任务的实践**，强调的是可靠的工具环境、可复用的技能模块、上下文压缩策略、中间状态的持久化。没有一条是关于"怎么让 Agent 扮演得更像真人"。

三家的做法不同，但共识惊人一致：**让 Agent 能做事的关键是执行面的稳定性和上下文的完整性，不是角色扮演的逼真度。**

## 真正有用的多 Agent 长什么样

### 并行探索型：Orchestrator + Workers

一个调度器拆任务，多个 worker 同时去不同方向找答案，最后汇总。适合调研、方案比选、信息收集这类天然可并行的场景。

这里的关键不是给 worker 编人设，而是把任务边界和返回格式定义清楚。

### 对抗验证型：Producer + Critic

一个负责产出，一个专门负责否定。适合代码审查、方案评审、安全检查。

**验证 Agent 的工作是找错，不是接棒。** 这个区分非常重要——大部分"虚拟公司"架构里的"测试 Agent"其实是在接棒，不是在对抗。

### 单 Agent + 强上下文：别小看它

很多任务需要的是深度推理、全局一致性、连续决策。这种场景下，一个上下文充分、工具链完整、状态管理稳定的单 Agent，效果远好于一群"文档接力"的多 Agent。

现在越来越多做得好的 agent 系统，核心投入都在 context engineering、external memory、persistent state、compaction 这些基础设施上，而不是在发明新的"岗位角色图"。

---

## 实操原则

如果你正在做多 Agent 系统，我建议按这个顺序思考：

1. **先把上下文和状态管理搭好** — 这是一切的地基
2. **再看哪些环节真的需要并行** — 并行探索比串行接力几乎总是更好的选择
3. **把验证环节独立出来** — 验证者必须是否定者，不是流水线上的下一站
4. **最后才考虑要不要加角色视角** — 作为 prompt 偏置可以，作为系统架构就算了

---

## 一个需要说清楚的边界

我不是说角色提示完全没用。让一个 critic 以"安全审查员"的视角审代码，确实能引导它关注特定维度。但这是**提示技巧**，不是**系统架构**。

区别在于：提示偏置是给单次推理加一个视角滤镜；而"虚拟公司"是把整个系统的信息流、决策链、质量门禁都建立在角色分工的假设上。前者轻巧有效，后者大概率翻车。

同样，也不是所有多 Agent 都该被否定。判断标准很简单：

- 任务天然可并行吗？
- 中间状态能低损耗地外化吗？
- 验证能独立于生产吗？

满足这些条件的多 Agent，仍然是非常有价值的架构选择。

---

## 最后

下次有人给你看一个多 Agent 架构图，上面画着"PM Agent → 架构师 Agent → 开发 Agent → 测试 Agent"，先问自己三个问题：

- 这是在解决真实的工程瓶颈，还是在让架构图更好看？
- Agent 之间传递的是完整上下文，还是压缩后的残片？
- 去掉角色标签、让一个 Agent 带着完整上下文直接做，效果会不会反而更好？

如果第三个问题的答案是"可能会"——那你大概率不需要那个"虚拟公司"。

你需要的是更好的上下文工程，不是更多的工牌。
